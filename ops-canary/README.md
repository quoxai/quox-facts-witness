# Operations canary: the track-record clock, started 2026-09-03

Every sceptical AI assessor who evaluated Quox with live web access on
2026-09-03 (benchmark round 5: one GPT-family run, two Claude-family runs)
returned the same verdict for six months of unattended operation: NO, not
because the machinery failed their checks, but because the machinery was
days old. Their unanimous cure, in the GPT assessor's words: "a
pre-committed, externally mirrored ... production-canary evidence bundle:
immutable daily checkpoints ... full incident/restart/upgrade history ...
It must include failures, not only happy-path receipts."

This directory is that clock, started the same night. It cannot be
backdated, and that is the point: day 0 is 2026-09-03, and every day of
history here had to actually happen.

## Protocol (pre-committed)

- One checkpoint per day (`day-NNNN/checkpoint.json`), generated by
  `canary-checkpoint.mjs` (in this directory, auditable), describing the
  observable operational state of the instance: collector health, per-
  container status with restart counts and restarted-in-last-24h flags,
  evidence-substrate counters, the facts-chain head that day, and an
  incidents field. Failures are recorded, never filtered; a metric that
  cannot be gathered says `unavailable` with the reason, never a made-up
  value.
- Each checkpoint is hashed and appended to a dedicated WARD chain
  (`ward:quox.ai/ops-canary`) whose full export lives here (`chain.json`):
  a skipped or deleted day is visible as a sequence gap to anyone.
- Each day's chain tip is Ed25519-signed with the SAME key that signs the
  quox.ai/facts chain. That key's public half has been embedded in every
  published facts.receipt.json and mirrored to this append-only repository
  since seq 1 (2026-09-02): the key was publicly pinned BEFORE the canary
  began.
- Each day's statement is countersigned by an RFC-3161 timestamp from
  freetsa.org (`statement.tsr`), a clock outside Quox's control, and the
  whole day is pushed to this repository, infrastructure Quox does not
  operate.
- The run is driven by a systemd timer with `Persistent=true`: a day the
  host was down runs late on next boot, and the late TSA time says so
  honestly.

## Verify a day yourself

    cd ops-canary/day-0000
    sha256sum checkpoint.json            # equals checkpoint_sha256 in statement.txt + receipt.json
    openssl ts -verify -data statement.txt -in statement.tsr -CAfile ../../freetsa-cacert.pem
    # and check receipt.json's ward_tip.sig is a valid Ed25519 signature by
    # public_key over ward_tip.tip_chain_hash (WARD spec section 12.2) —
    # the same check facts.receipt.json documents.

## Honest limitations, stated up front

- This observes the DEVELOPMENT instance (labeled dev-1). The production
  canary needs the owner's sign-off and will be labeled as its own series
  when it starts; nothing here claims production history yet.
- A daily snapshot is not continuous monitoring: an incident that starts
  and fully resolves between checkpoints shows up only via restart counts
  and the incidents file.
- The checkpoint generator runs on the instance it observes. The external
  guarantees are the TSA countersignature, the pre-pinned key, and this
  append-only history; the metric VALUES are still self-reported, the same
  boundary every facts.receipt.json states.
- Day counting starts at 0 on 2026-09-03. Anyone quoting "N days of
  history" can recompute N from the directory listing and the TSA times.
